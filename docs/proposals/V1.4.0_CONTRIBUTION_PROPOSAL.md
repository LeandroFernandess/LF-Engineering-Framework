## Purpose

Record bounded pilot evidence, the independent Elephant-Goldfish evaluation and
the owner-approved contribution scope for the `v1.4.0` release.
Approval is limited to optional reference status; it does not claim general
effectiveness or promote the modules to mandatory Framework dependencies.

## Pilot Findings

Evidence classes are kept separate: direct observations are not equivalent to
vendor claims, and a successful preflight is not a full representative pilot.

### 1. Elephant-Goldfish — partial workflow pilot

Approved optional module: `knowledge/ENGINEERING_ELEPHANT_GOLDFISH.md`.

**Observed:** The isolated motion-design client sandbox used durable project brief,
requirements, architecture, ADR and sprint artifacts before implementation.
Acceptance criteria and file scope were written down and approved before code;
the implementation remained dependency-free. Browser evidence and review/QA
reports were then recorded. Initial mobile screenshots exposed a layout defect
that was corrected before final evidence.

**Independent Goldfish evaluation (2026-11-01):** Three separate fresh sessions
received the same durable design packet. Comprehension passed with
qualifications; critic and implementation-readiness checks failed. The detailed
report is `docs/evaluations/ELEPHANT_GOLDFISH_MOTION_DESIGN_2026-11-01.md`.

**Limitations:** The work was a small static page rather than a medium-complexity
feature or legacy change. The evaluation was retrospective and tested artifacts,
not the implementation. The implementation, review and QA occurred in one
session. No matched control or reliable time/rework baseline was run.

**Owner-approved optional disposition:** Include the module as optional guidance
for the `v1.4.0` candidate, without a universal design gate or required artifact.
The comprehension result shows the packet was understandable with qualifications;
failed critic/readiness results mean the full loop did not pass and the packet is
not one-pass implementation-ready. The evaluation is not evidence of reduced
rework or general effectiveness.

### 2. Agent Graph Flow — small disposable workflow pilot; effectiveness unvalidated

Approved optional module: `knowledge/ENGINEERING_AGENT_GRAPH_FLOW.md`.

**Initial preflight:** The already-present local CLI reports `agf 0.24.2`. A
read-only `agf status` in this Framework checkout returned `Graph not
initialized`; no state was created in the Framework repository.

**Follow-up isolated pilot (2026-11-01):** In a disposable Python project under
an owner-only temporary root and temporary `HOME`, `agf init --graph-only
--skip-neural --no-serve --no-open` created a graph store and `.gitignore` in
the project; no project context files, hooks, dashboard or server were created.
Two task nodes and one `depends_on` edge were added. A textual query returned
both tasks, the JSON export retained the edge, and both statuses were manually
advanced to `done` after four standard-library `unittest` checks passed. No
installation was performed; no provider, MCP, daemon or dashboard was enabled.
The requested project name did not appear in the exported metadata, which
instead showed `Local MCP Graph`; the cause was not investigated.

The disposable graph was initially created with directory mode `0755` and
`graph.db` mode `0644`; the `umask` used for the initialization command was not
recorded, so this pilot does not establish whether AGF respects a restrictive
umask. The temporary graph and files were changed to modes `0700`/`0600` after
observing this. The CLI also created a token-economy configuration under the
temporary `HOME`. An initial mistyped node ID returned `NOT_FOUND` without
changing the graph; a first test
invocation from the wrong working directory failed to import the fixture and
passed when rerun from the project root. These were operator errors, not tool
defects.

**Limitations:** This was a tiny synthetic feature, not representative client
work. No control project, comparison with `.ai/` handoffs, cross-session
recovery, independent review, or time/rework baseline was measured. The status
field was manually advanced and is not proof of implementation correctness.

**Owner-approved optional disposition:** Include the module as optional guidance
only. Do not add a mandatory CLI, graph gate, skill, or second source of truth.
The pilot shows basic graph-only task/dependency recording and retrieval, but
not delivery value. File permissions, generated state and graph/artifact
ownership remain explicit concerns. Installation or integration requires
separate, specific owner approval.

### 3. RTK — bounded manual and isolated-output experiments

Approved optional module: `knowledge/ENGINEERING_RTK.md`.

**Environment and checks:** The pre-existing local binary reports `rtk 0.47.0`.
`rtk verify` reported 154/154 checks passed, owner-only data-directory
permissions, and explicitly skipped the hook because none is installed.
`rtk telemetry status` reported never consented, disabled, and no salt file.
No hook, plugin, telemetry, configuration, or package installation was changed.

**Experiment:** Compared `git log --oneline --decorate -20` with the equivalent
manual `rtk git log --oneline --decorate -20` in this documentation repository.
Both commands exited `0`; all 14 commit IDs were present in both outputs. Raw
output was 744 bytes and filtered output 724 bytes, a 2.7% reduction. RTK
truncated the first commit subject (`feat: add conditional motion design
guidance` became `feat: add conditional...`). One timing sample was approximately
13.46 ms raw versus 30.31 ms filtered; this is too small and noisy to establish
overhead or savings.

**Follow-up isolated comparisons (2026-11-01):** The preinstalled `rtk 0.47.0`
was run manually against a disposable local Git/Python fixture, with a temporary
`HOME`, `RTK_TELEMETRY_DISABLED=1`, no hooks/plugins and no package installation.
Exit codes matched for all four comparisons. `git status` changed 54 to 53
bytes (1.85% reduction), `git diff` changed 1,342 to 1,339 bytes (0.22%), and
`rg` remained 254 bytes (0%). One deliberately failing 9-test `unittest` run
changed 1,521 raw bytes to 222 filtered bytes (85.4%); both commands returned
exit code 1. The compact result reported one failure and supplied a full-output
path, but omitted the eight passing test names and the failing assertion and
traceback. For these fixtures, status formatting changed `## main` to `* main`;
the diff filter retained changed hunks but removed some Git metadata headers;
`rg` returned the same matches in a different order.

The tee file in the temporary RTK home was byte-for-byte equal to the raw test
output. `rtk run -c 'python3 -m unittest discover -s tests -v'` also reproduced
the raw stdout, stderr and exit code exactly. The installed binary does not
expose the `rtk recall` command shown in newer public documentation. RTK's
temporary history database and tee directory were owner-only. Single timing
samples varied by command and are too small/noisy to establish overhead or
savings; no provider-token or billing data was collected.

**Owner-approved optional disposition:** Include the module as optional guidance
only. Test-output compaction with a usable raw-recovery path is promising, but
this fixture shows negligible reduction for status, diff and search, and the test
summary alone cannot support diagnosis. Recovery and semantic loss must remain
explicit; the experiment does not justify hooks, plugins, installation or a
cost-saving claim. Tool installation or integration requires separate, specific
owner approval.

### 4. Graphify — isolated code-only pilot; source-to-build provenance remains incomplete

Approved optional module: `knowledge/ENGINEERING_GRAPHIFY.md`.

**Identity and provenance evidence checked on 2026-11-01:**

Sources: [official-site verification](https://graphify.com/graphify-net-vs-graphify-com),
[GitHub repository](https://github.com/Graphify-Labs/graphify),
[v0.9.100 release](https://github.com/Graphify-Labs/graphify/releases/tag/v0.9.100),
[tagged package metadata](https://raw.githubusercontent.com/Graphify-Labs/graphify/v0.9.100/pyproject.toml),
[PyPI project metadata](https://pypi.org/pypi/graphifyy/json), and the
[versioned CLI README](https://raw.githubusercontent.com/Graphify-Labs/graphify/v0.9.100/README.md).
Follow-up sources: [PyPI wheel provenance](https://pypi.org/integrity/graphifyy/0.9.100/graphifyy-0.9.100-py3-none-any.whl/provenance),
[PyPI attestation documentation](https://docs.pypi.org/attestations/), and the
[GitHub publish workflow run](https://github.com/Graphify-Labs/graphify/actions/runs/41258715089).

- The Graphify official-site verification page identifies `graphify.com`,
  `Graphify-Labs/graphify`, and the PyPI package `graphifyy` as its official
  sources; it says the supplied `graphiffy.com` domain no longer resolves.
- GitHub repository metadata identifies the public Apache-2.0 repository and
  `v8` default branch. The repository's release `v0.9.100` and its tagged
  `pyproject.toml` identify package/version `graphifyy 0.9.100`; PyPI metadata
  links back to the same homepage and repository.
- The GitHub `v0.9.100` release lists a wheel named
  `graphifyy-0.9.100-py3-none-any.whl` with SHA-256
  `577d917d1282a87cc9e31e237b0073bf7e0f4f258503a698f38d8e0af4eed072`.
  PyPI lists the same filename/version with SHA-256
  `64c5ed6f2dcc8c28b6a96c87023851c1644c16f55a87f45dbc9127119eb6e769`.
  These are different artifacts; the mismatch does not by itself prove
  compromise, and a matching release-asset relationship was not established by
  hash comparison.
- GitHub reports the `v0.9.100` tag and release commit as unsigned. The PyPI
  project JSON response exposed no provenance field and an initial integrity
  URL lookup returned 404. The current `v8` branch head
  (`32e5efe935e6844ef39a5e33409e4efe848f2172`) is later than the release and
  references unreleased `0.9.101` work; do not treat branch head as the release.
- **Follow-up public provenance verification (2026-11-01):** A repeat request to
  the PyPI integrity endpoint returned a PEP 740 PyPI Publish Attestation for
  the exact PyPI wheel. Its subject digest matches the retained one-time test
  wheel (`64c5ed6f…`). Using the already available `cryptography` library (no
  new tool installation), local checks verified the DSSE ECDSA P-256/SHA-256
  signature, the leaf/intermediate signatures to a current Sigstore trusted
  root, and certificate validity at the transparency entry's integrated time.
  The attested publisher is GitHub repository `Graphify-Labs/graphify`, workflow
  `publish.yml`; the certificate identity is that workflow on
  `refs/tags/v0.9.100`. The bundle contains a transparency entry, but its
  inclusion proof was not independently verified in this check.
- The public GitHub Actions run `41258715089` completed successfully for commit
  `f5155badddaa3286c78a51653791131e9e2e4d29` at `v0.9.100`; its steps show
  checkout, `uv build`, version/tag guard, Twine metadata check, and trusted
  publishing. This is useful source/workflow evidence, but the attestation
  predicate is **PyPI Publish**, not SLSA build provenance: it binds the wheel
  digest to the trusted publisher identity, not a signed source-to-build
  statement. The tag is unsigned. The GitHub Release wheel SHA-256
  (`577d917d…`) still differs from the PyPI wheel (`64c5ed6f…`); the attached
  sdist hashes also differ (`14d0e0a8…` vs. `bb089c59…`). The reason for those
  separate release assets remains unknown.

**Owner-authorized exception:** After reviewing the mismatch, the Project Owner
explicitly authorized a one-time isolated test of `graphifyy==0.9.100`. The
wheel was downloaded from `https://pypi.org/simple`, and its computed SHA-256
matched the PyPI JSON value and the PyPI attested subject above, not the GitHub
release asset value. It was installed in a dedicated Python 3.11.15 virtual
environment under a temporary directory outside this repository. The environment
resolved 31 distributions in total; no global Python environment was changed.
No additional installation occurred during the follow-up.

**Runtime scope and result:** The pinned CLI was run directly, without invoking
or installing its assistant skill. A disposable four-file Python fixture
contained `handle()`, `route()`, `normalize()`, a dynamic `handler(path)` call,
and one test. The fixture's direct Python test returned the expected `/home`.
With a clean environment, `GRAPHIFY_BACKEND=none`, query logging disabled,
`--code-only`, `--no-cluster`, and an output directory outside the fixture,
Graphify found four code files and zero documents, papers, or images. It wrote
9 nodes and 16 edges: 5 `contains`, 4 `imports`, 4 `calls`, and 3
`imports_from`; no semantic extraction or clustering was requested. The output
included `graph.json`, manifest, and AST cache; no HTML, report, hook, MCP
server, skill, or project configuration was created.

**Fixed-question check:** `graphify query "Which functions call normalize?"`
returned `route()` and `handle()` through extracted call edges. `graphify path
"handle()" "normalize()"` returned the source-confirmed two-hop path
`handle() → route() → normalize()`, and `explain` cited
`src/normalize.py:L1` and `src/routing.py:L5`. Direct comparison with the
fixture confirmed those edges and locations. The dynamic call
`resolve(handler, ...) → handler(path)` did **not** appear in the graph; the
known unresolved relationship is a false negative for this fixture, not proof
that the tool supports dynamic dispatch. One small Python fixture does not
measure broader language coverage, stale-graph behavior, recall, latency, token
savings, or production value.

**Owner-approved optional disposition:** Include the module as optional guidance
only. The PyPI wheel's exact digest and Trusted Publisher identity are
cryptographically linked, but source-to-build provenance remains incomplete:
the PyPI attestation is not SLSA provenance, the tag is unsigned, GitHub Release
assets differ, and the transparency inclusion proof was not independently
checked here. Approval of the written module does not authorize further
installation or broader evaluation. Any future tool use requires separate
specific owner approval and an explicit provenance threshold; it must remain
disposable and code-only, without `graphify install`, hooks, MCP, semantic
document processing or cloud credentials.

## Authorized v1.4.0 Release Scope

The Project Owner authorized a `v1.4.0` release from the reviewed maintenance
delta and the four modules as approved optional references, subject to the full
diff audit and release gates. Any changed files not represented by
that scope must be escalated before inclusion. This approval does **not**
authorize any of the following:

- Changing the default workflow or adding a mandatory phase/artifact.
- Promoting the four modules to the mandatory stable dependency graph.
- Adding a third-party dependency, CLI, hook, plugin, MCP server, telemetry, or
  provider requirement to the generic bootstrap.
- Making production-readiness claims from the client pilot or tool
  preflights.

The modules are marked `Approved Optional` and remain separate from mandatory
agent instructions, workflows, schemas, templates and dependencies. The
independent Goldfish findings remain linked evidence, not a successful readiness
claim. ADR-014 records the decision; EN-US and PT-BR records and validators must
remain synchronized.
