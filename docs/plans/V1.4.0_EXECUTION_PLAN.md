# v1.4.0 Release Execution Plan

**Status:** Historical record of the stable `v1.4.0` release in the predecessor
private repository on 2026-11-01. The exact-tag Ubuntu/macOS/Windows matrix,
packaging and tag mapping check passed. The automatic publish job failed because
it lacked a Git checkout; after owner authorization, the verified workflow
archives and checksums were published manually. A checkout/local-tag verification
fix was completed afterward. The predecessor's tag, CI runs and Git history were
not migrated into the public repository; the first public release is `v1.5.0`.<br>
**Owner:** Project Owner / Framework Maintainer<br>
**Date:** 2026-11-01<br>
**Baseline:** Historical `v1.3.0` baseline in the predecessor private repository.

## Objective

Prepare the authorized `v1.4.0` release by reconciling the reviewed Framework
maintenance with the four owner-approved optional supplemental
Knowledge modules, preserving the existing `generic` default and published
`v1.3.0` artifacts.

## Approved Scope and Boundaries

- Include the reviewed maintenance delta plus the four modules as **approved
  optional references**, subject to the full diff audit and release gates. Do not
  add unlisted behavior or dependencies.
- Keep all four modules outside the mandatory dependency graph, default agent
  knowledge, universal workflow gates and required artifacts.
- Treat module approval as approval of written guidance only. It does not
  authorize installing or activating AGF, RTK or Graphify, or adding CLIs,
  packages, hooks, plugins, skills, MCP servers, providers, telemetry or generated
  state. Graphify's source-to-build provenance gap remains unresolved.
- Record the independent Elephant-Goldfish result accurately: comprehension
  passed with qualifications; critic and implementation-readiness did not pass.
  Do not claim that the pilot was successful, representative, production-ready or
  ready for one-pass implementation.
- Keep `generic` as the bootstrap default. Do not alter the published `v1.3.0`
  tag, archives or checksums.
- The owner selected public inclusion of the four candidate plan/evaluation
  documents in sanitized form. Remove OpenCode session IDs and owner-local paths
  or project identifiers before those documents enter the public candidate.
- The owner authorized the `v1.4.0` tag push and automatic release workflow on
  2026-11-01. The exact tagged commit must pass the Ubuntu/macOS/Windows matrix
  before packaging and publication; do not bypass or manually replace these gates.

## Risks and Controls

| Risk | Control |
|---|---|
| “Approved optional” is mistaken for mandatory or stable dependency adoption. | Repeat the boundary in ADR, module headers, registries, template guidance and release notes; validate statuses. |
| Module approval is mistaken for permission to install tools. | Keep each external integration separately gated; retain Graphify's unresolved provenance hold. |
| Goldfish findings are hidden by the user's adoption decision. | Publish the exact three-test outcomes and avoid a successful-pilot claim. |
| The post-`v1.3.0` delta is substantial. | Compare the complete release diff and changelog scope; escalate unlisted changes. |
| A moved release tag could select untested code or reach a shell. | Validate stable tag syntax before fetching, pass inputs through environment variables, test and package a resolved commit, recheck the remote tag, and verify the tag during release creation. |
| A release job could publish without cross-platform validation or use a write token while packaging. | Require the reusable Ubuntu/macOS/Windows matrix; build and transfer immutable artifacts in a read-only job; grant `contents: write` only to the publish job. |
| `gh release create --verify-tag` runs without a local Git repository in the publish job. | Check out the exact release tag with `persist-credentials: false`; verify the checked-out tag resolves to the tested SHA and retain the remote API recheck before publication. |
| A matching tag push publishes automatically without a reviewer pause. | Keep write/admin access with the sole owner; require separate owner authorization before pushing a tag; retain the exact-tag matrix and tag-to-commit checks. Reassess if write access expands. |
| A terminal agent may read outside a disposable client project despite the requested boundary. | Stop further CLI runs after an out-of-boundary read; require a verified isolation mechanism and renewed owner authorization before resuming. |
| Release is treated as authorized merely because candidate preparation is approved. | Require explicit owner authorization before the tag push; authorization was recorded on 2026-11-01. Enforce exact-tag CI and tag-to-commit checks before publication. |
